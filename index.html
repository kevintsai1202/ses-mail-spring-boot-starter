為什麼自建

三個優點

自建大量寄信伺服器

電子報、廣告信都能寄。群發整批寫入佇列，派送器依速率送出，可以排程、可以取消；重試和額度計算都在自己的程式裡，可測、可查、可換服務商。

廣告信要收件人事先同意、每封附退訂連結；SES 審核生產存取權時也會看這兩點。

事件接收自己選

退信、檢舉、送達事件可以用 SQS 拉取：停機、重新部署都不漏，處理失敗會重試，最後進死信佇列。也可以用 webhook 讓 SNS 直接推，少建一個佇列。換方式只改設定，事件處理程式不用動。

價格便宜

SES 每千封 $0.10，每月寄 5 萬封約 $5。託管型服務的 Pro 方案是 $19～20／月，入門方案每天只能寄 100 封，連一期 310 人的電子報都寄不完。

代價

選之前要先知道的兩件事

要自己維護伺服器

派送器跑在你的 Spring Boot 程式裡，程式要一直在線，停機期間排程信不會寄出。待寄佇列存在你的 PostgreSQL，AWS 的網域驗證、IAM、SNS、SQS 也要自己顧。

一天超過 200 封要先申請

SES 新帳號在沙箱裡：每天最多 200 封、每秒 1 封，而且只能寄給驗證過的信箱。要正式寄送得申請生產存取權，AWS 會審核用途，通過後通常是每天 5 萬封。

AI agent 技能

開發與設定都寫成技能

ses-mail-setup 把導入步驟寫成 AI agent 照著做的流程，採用開放的 Agent Skills 格式，Claude Code、Codex、Cursor、Gemini CLI、GitHub Copilot 等工具都能用。開工前會先問你：事件要用 SQS 拉取、webhook，還是不接收。接著依序帶你完成：

  1. 整合 starter：加依賴、套用 yaml 範本、建表、寫寄信與事件 Listener。
  2. 建立 AWS 資源：在 CloudShell 執行腳本，先用 -DryRun 預覽。網域驗證、configuration set、SNS、SQS、IAM、信譽警報一次建好，可以重複執行。
  3. 申請離開沙箱：附用途說明範本，審核結果用腳本就能查。
  4. 上線維運：死信佇列、卡在 SENDING 的信、停用或換接收方式。
在你的專案根目錄執行 
npx skills add kevintsai1202/ses-mail-spring-boot-starter --skill ses-mail-setup

  • 會偵測你裝了哪些 agent 讓你選；要指定就加 -a codex、-a cursor、-a claude-code，需要 Node.js 22.20 以上。
  • 不用 npx 也行：把 skills/ses-mail-setup 資料夾複製到工具的技能目錄，多數工具是 .agents/skills/，Claude Code 是 .claude/skills/。
  • 不支援技能的 agent：執行 npx skills use kevintsai1202/ses-mail-spring-boot-starter@ses-mail-setup 印出提示詞，貼給它照做。
  • 建資源的腳本在 AWS CloudShell 執行；存取金鑰的 secret 不經過對話，由你直接貼到部署平台。

架構對照

託管型和自建型，差在哪裡

託管型寄信服務（ZSend、Resend）把佇列、排程、重試和事件都放在服務商那端；自建型把這些搬進 starter，SES 只負責投遞。

服務商負責  託管型：ZSend、Resend

  • 程式最少：呼叫 API 就好，批次、排程、取消都由服務商做。
  • 看不到內部：信卡在哪、重試幾次、為何失敗，只能看服務商給什麼。
  • 受方案額度限制：兩家的入門方案都是每天 100 封，要升級才拿掉每日上限。
    • ZSend：額度綁在 Zeabur 主機訂閱裡，Free 方案不能用。Dev 方案 $5／月，每天 100 封、每月 3,000 封；Pro 方案 $19／月，每月 5 萬封、不限每日，超額每千封 $0.90。
    • Resend：免費每天 100 封、每月 3,000 封；Pro $20／月，每月 5 萬封。

自己負責  自建型：Amazon SES ＋ ses-mail-spring-boot-starter

  • 費用最低：每千封 $0.10，我們的用量每月約 $0.3。
  • 行為都在自己手上：佇列、排程、取消、重試、額度計算都是自己的程式，可測、可查、可換服務商。
  • 代價是 AWS 營運：網域驗證、離開沙箱審核、IAM、SNS、警報都要自己顧；選 SQS 再多一個佇列。

SNS 做什麼

SES 只會把事件丟到 SNS topic。SNS 負責轉發：可以直接 POST 到你的服務（webhook），也可以送進 SQS 佇列，日後還能再加 email 通知。它不負責保存，推給你的服務失敗時只重試約 1 分鐘，之後就沒了。

SQS 做什麼（可選）

SQS 負責保管：事件放進佇列後，由我們的程式定時來拉。部署、重啟或資料庫出錯時事件留在佇列裡，程式恢復後再處理；一直處理不了的會移到死信佇列，方便事後查。

事件接收

SQS 要不要，自己選

兩種方式共用 starter 同一套驗簽、topic 白名單與事件處理，你只寫一次 SesEventListener。差別只在事件怎麼進到程式，用設定開關切換，只開一個。

方式 A：加 SQS，程式主動拉

sesmail.sqs.enabled=true。SNS → SQS 佇列 → starter 每次長輪詢 20 秒，有事件就立刻回來處理。停機、重新部署、資料庫出錯都不漏，處理失敗會重送，5 次仍失敗進死信佇列。不用對外開端點。

方式 B：不用 SQS，SNS 直接推

sesmail.sns.enabled=true。SNS 直接 POST 到 starter 內建的接收器 /sesmail/sns，訂閱確認、驗簽都自動處理。少建一個佇列，但服務停機時 SNS 只重試約 1 分鐘，處理失敗也不會重送。

排程

時間到了誰來寄

兩種做法差最多的就是這裡。託管服務自己有排程器；SES 只會「現在寄」，排程得由我們的程式自己跑。

託管型：交給服務商的排程器

呼叫排程 API 時帶上寄送時間（ZSend 的 /emails/schedule、Resend 的 scheduled_at），服務商存起來，時間到由它寄出；取消也是呼叫 API。寄送當下我們的程式停機也沒關係。

自建型：starter 的派送器自己跑

排程信先寫進 scheduled_mail，附上寄送時間。程式裡的派送器每 10 秒掃一次，撈出到期的信（一輪最多 200 封），逐封認領後依速率交給 SES。程式沒在跑，信就不會寄出。

  • 程式要在線：重新部署或停機期間不會寄；恢復後會補寄已過時間的信，晚到但不遺失。
  • 準時程度：最多晚一個掃描間隔（10 秒，可用 sesmail.dispatch-interval 調整），再加上限速排隊。每秒 5 封時，310 封約 1 分鐘寄完。
  • 取消不會跟派送打架：認領和取消都是條件式更新，已被認領的信取消不了，已取消的信不會被寄出。
  • 重試與卡住：暫時性錯誤從 30 秒起倍增退避，最多 5 次。程式在送信途中當掉時，已認領的信會停在處理中；超過 10 分鐘會記警告，交由人工確認，不自動重寄，以免讀者收到兩封。

自己管理

SES 方案適合誰

自建型適合有能力自己架設、維運伺服器的團隊：程式要一直在線，資料庫自己顧，AWS 主控台也要有人會操作。寄信本身很便宜，代價是下面這些事都由你負責；導入技能會一步步帶你做完。

主機與程式

  • 常駐的 Spring Boot 服務：派送器和 SQS 拉取器都在程式裡跑，程式停了就不寄信、也不收事件，不適合會自動休眠的主機。
  • PostgreSQL：待寄佇列 scheduled_mail 存在你的資料庫。建表、備份、升級 starter 時補上新的 migration，都要自己做。
  • 卡住的信：程式在送信途中中斷時，信會停在 SENDING。starter 不會自動重寄，要人工確認讀者沒收到，再改回待寄。
  • 對外端點（只有方式 B）：要有公開的 HTTPS 網址，而且不能被登入或 Host 白名單擋住。

AWS 帳號設定

  • 網域驗證：在 DNS 加上 SES 提供的記錄，驗證通過才能用自己的網域寄信。
  • 離開沙箱：申請生產存取權，說明寄信用途並等待審核；之後要調高額度也是自己申請。
  • IAM 與金鑰：寄信和查額度只需要 ses:SendEmail、ses:GetAccount，方式 A 再加讀佇列的三項權限。存取金鑰的保管與更換也要自己來。
  • configuration set：把 Bounce、Complaint、Delivery 事件送到 SNS topic。用了它就不要再開身分層級的回饋通知，否則同一封退信會收到兩次。

寄出之後

  • 事件管線：SNS topic，加上 SQS 佇列和死信佇列（方式 A），或 HTTPS 訂閱（方式 B）。
  • 死信佇列要有人看：處理失敗 5 次的事件會在這裡留 14 天，過期就沒了。
  • 信譽警報：在 CloudWatch 設退信率、檢舉率警報。比率太高時 AWS 會審查帳號，甚至暫停寄信。
  • 停寄名單：SES 帳號層級的停寄名單會擋下退信或檢舉過的地址，要恢復寄送得自己去移除。

沒有人手顧主機和 AWS，或寄量在每天 100 封以內，選託管型服務比較省事。
